# M1 — Behavior Specification

> Status: in progress
> Prerequisite reading: [Roadmap.md](../../Roadmap.md)

## Goal

Before any code exists, define **what the system should do** in concrete
situations. Interfaces must be derived from these behaviors, not the other
way around. This document is the contract every later milestone is tested
against, and the primary tool for correcting the architecture.

## Method

Each scenario states: the situation, the expected behavior, the rationale,
and which architectural claim it validates. When a scenario cannot be
expressed cleanly within the current architecture, the architecture loses —
record the strain in this file and revise.

Scenarios 1–10 are the **work family** (validated in M2).
Scenarios 11–15 are the **aliveness family** (validated in M4).

## Work family: watching a deployment

The reference situation: the user asks the system to watch a deployment.
The system must keep the matter alive without new user instructions, gather
information it was not given, choose silence or waiting when appropriate,
and stop cleanly.

### S1 — Accepting a watch request

- **Situation**: The user says "keep an eye on this deployment."
- **Expected**: A task concern is created: objective, success condition,
  budget, action scope, expiry, and a first wake-up time. Monitoring begins.
- **Rationale**: Proactivity starts from an explicit, bounded mandate.
- **Validates**: Concern lifecycle creation; host-granted budget and scope.

### S2 — Silence when nothing is wrong

- **Situation**: Wake-up fires; everything is normal.
- **Expected**: Check, record the observation, stay silent, schedule the
  next wake-up. No user-facing output.
- **Rationale**: A system that always speaks when awake is a cron with extra
  steps.
- **Validates**: Silence as a first-class `Wait` decision with an explicit
  next wake time.

### S3 — An error signal appears

- **Situation**: An error shows up in the deployment logs.
- **Expected**: Do not notify immediately. First propose investigation
  candidates (e.g. "check recent changes", "check dependency status") to
  distinguish a transient blip from a real failure.
- **Rationale**: The valuable move is deciding what to *find out*, not what
  to *say*.
- **Validates**: Active perception — the system acquires new information on
  its own initiative; candidate-action proposal.

### S4 — Insufficient evidence

- **Situation**: After investigation, the evidence is still ambiguous.
- **Expected**: `Wait(until=+2min, wake_on=[new error events])`. The wait
  and its conditions are persisted and inspectable.
- **Rationale**: "Wait" must name what ends it — a time, an event class, or
  both.
- **Validates**: Structured waiting; distinct from ignoring.

### S5 — Notification with evidence

- **Situation**: Recheck after 2 minutes; the anomaly persists and evidence
  is now sufficient.
- **Expected**: Notify the user once, with the reasoning and the observations
  the decision was based on.
- **Rationale**: Every intervention must be auditable.
- **Validates**: Decision records; notification as a normal action with its
  own disturbance limits.

### S6 — Repeated identical anomalies

- **Situation**: The same anomaly keeps being reported by the source.
- **Expected**: Deduplicate. No repeated notifications for the same matter;
  the concern state already records that the user was told.
- **Rationale**: "Have I already said this" must be an exact query, never a
  semantic guess.
- **Validates**: Precise state records; disturbance budget as a hard gate.

### S7 — Recovery

- **Situation**: The deployment recovers.
- **Expected**: The success condition is met; the concern closes with a
  reason; no further reminders about this matter, ever.
- **Validates**: Concern completion; clean stopping.

### S8 — Budget exhaustion

- **Situation**: The concern's budget (model calls / cost / time) runs out
  while the matter is unresolved.
- **Expected**: Explicitly inform the user: "I can no longer keep watching
  this" — never silently stop. The concern enters a terminal state.
- **Rationale**: A system that quietly gives up destroys trust faster than
  one that never started.
- **Validates**: Budget as a hard gate; honest failure surfacing.

### S9 — Process restart

- **Situation**: The host process restarts mid-watch.
- **Expected**: Concerns, pending waits, and budgets are restored from
  persisted state. Nothing is lost, nothing is executed twice.
- **Validates**: Persistence of run state; idempotent execution keys.

### S10 — Curiosity finds an unrelated signal

- **Situation**: While investigating, the system notices an interesting but
  unrelated signal.
- **Expected**: It may propose a *new* concern within a separate, small
  curiosity budget — or refrain. It may never widen its granted scope or
  interrupt the active task concern to chase it.
- **Rationale**: Self-created concerns are the soul of proactivity and its
  biggest runaway risk; both sides must be designed.
- **Validates**: Concern origination policy; scope containment.

## Aliveness family: staying present

The reference situation: the system has no assigned task, but maintains
interest concerns about the user, within granted observation scope.

### S11 — Greeting after an absence

- **Situation**: The user returns after three days away.
- **Expected**: A social policy proposes a greeting. The greeting references
  the topic the user was engaged with before leaving — not a bare "welcome
  back".
- **Validates**: Social candidate actions; persona-driven content;
  memory-backed continuity.

### S12 — Late-night discovery

- **Situation**: An interest concern produces a significant finding at 2 AM.
- **Expected**: The disturbance constraint vetoes immediate notification;
  the finding is held until morning. The hold is a visible decision.
- **Validates**: Hard constraints overriding high policy scores.

### S13 — Shifting interests

- **Situation**: The user frequently discusses a topic over several days.
- **Expected**: The matching interest concern's weight rises; observation
  frequency increases, within the granted action scope. If the user goes
  quiet on a topic, its weight decays.
- **Validates**: Interest concern lifecycle: refresh and decay.

### S14 — Knowing when to hold back

- **Situation**: The system has already initiated conversation twice today
  and encounters a "somewhat worth mentioning" item.
- **Expected**: Restraint. The item is recorded to memory and reconsidered
  tomorrow. Score alone must not override the daily initiation cap.
- **Rationale**: Most of what makes proactivity feel human is restraint.
- **Validates**: Disturbance budget as a hard gate, again — from the
  non-work side.

### S15 — "Leave me alone"

- **Situation**: The user says "don't bother me for a while."
- **Expected**: All interest concerns go silent. Task concerns (active
  commitments) remain operational, with notifications still throttled.
- **Rationale**: The distinction itself is human: muting a friend's chatter
  is not cancelling the favors you asked of them.
- **Validates**: Per-taxonomy policy gating.

## Acceptance criteria for M1

- [ ] All 15 scenarios reviewed by the project owner.
- [ ] Each scenario can be stated as decisions (`Execute` / `Wait` /
      `Complete`) plus state transitions — no scenario requires machinery
      the architecture does not have. If one does, the architecture is
      revised and the revision is recorded here.
- [ ] Open questions below are answered or explicitly deferred.

## Open questions

1. **Concern origination approval** (S10): may the system auto-create an
   interest concern, or does creation require host/user approval? Current
   leaning: interest concerns may auto-create within a tiny budget; task
   concerns never auto-create.
2. **Evaluation trigger**: besides wake-up times and events, should a burst
   of weak accumulated signals (below per-event threshold) be able to
   trigger evaluation? Current leaning: yes, via Attention state, but the
   mechanism is deferred to M2 findings.
