# M2 — Prototype: Deployment-Watch Scenario

> Status: pending
> Prerequisite reading: [Roadmap.md](../../Roadmap.md), [M1.md](M1.md)

## Goal

Prove that a system built on the Concern-centered architecture can sustain
**useful, restrained proactive behavior** in one concrete scenario — before
any general plugin machinery exists.

This milestone validates *correctness* (work family, scenarios S1–S10).

## What to build

A single-purpose prototype that watches a (simulated) deployment:

1. **One concern type**: the deployment watch, with objective, success
   condition, budget, action scope, expiry, wake-up schedule.
2. **One decision loop**: context snapshot → candidate actions → hard
   constraint filter → select one step → execute or wait.
3. **Minimal event sources**: a timer source and a scripted log source
   (replayable event files, so runs are reproducible).
4. **Minimal effectors**: a log-query stub and a "notify user" effector
   that prints.
5. **Plain persistence**: SQLite for concern state, decisions, and outcomes.

Deliberately naive implementations are correct here: rule-based candidate
scoring, one structured model call at most per evaluation, no generic
plugin interfaces.

## Explicit non-goals

- No generic `EventSource` / `Policy` / `Arbiter` plugin system.
- No interest concerns, persona, or social policies (that is M4).
- No distributed anything. Single process, single host.
- No vector database. Exact state queries only.

## The four proofs

The prototype passes only if it demonstrates all four, from M1:

1. **Continuation without instruction** — the concern advances on wake-ups
   alone (S2, S4).
2. **Self-initiated information gathering** — the system acquires
   information it was not given (S3).
3. **Chosen silence and waiting** — with explicit, inspectable conditions
   (S2, S4, S6).
4. **Clean stopping** — on completion, cancellation, or budget exhaustion,
   with honest surfacing (S7, S8).

Plus the robustness scenarios: dedupe (S6) and restart recovery (S9).

## Baseline comparison

Run the same replayed event sequences through a baseline:
"fixed-interval check + simple threshold rules". Compare on:

- **Useful interventions**: how many notifications were genuinely warranted.
- **Misses**: how many important changes went unnoticed.
- **Duplicates / noise**: repeated or pointless notifications.
- **Detection latency**: time from real anomaly to correct notification.
- **Wasted investigation**: checks that changed nothing.
- **Cost**: model calls, tokens, wall time per effective intervention.

A scenario pack (normal / anomaly / recovery / duplicate events / restart)
replayed end-to-end is the evidence — not a demo video of a happy path.

## Architecture feedback

Every point where the implementation fights the M1 architecture gets an
entry in M1's strain log. Expected candidates, from prior discussion:

- Where does "what to say" generation live, given "whether to act" is
  decided first? (Current leaning: candidate actions carry drafts.)
- How does Attention update state for events it declines to deep-process
  (weak-signal accumulation)?
- Does one evaluation per concern per cycle suffice, or do concerns
  interact?

## Exit criteria

      beat rules, and at what cost.
- [ ] Strain log entries recorded in M1.md.
- [ ] A short `NOTES.md` for the next session: what was learned, what M3
