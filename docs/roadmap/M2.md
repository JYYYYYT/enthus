# M2 — Continuous Co-presence Prototype

> Status: in progress
> Behavior: [M1 S26-S32, S35](M1.md#scenarios); meaning: [Roadmap CP1-CP7](../../Roadmap.md#continuous-presence-contract).

## Goal and scope

Demonstrate a companion that keeps receiving a changing shared environment,
participates without a fresh question, accepts interruption, and remains
receptive during silence. Use one user, one shared visual surface, bidirectional
voice, one model/provider path, bounded context, and one local host.

Choose a single shared activity. Use existing model capabilities and a minimal
media-capable UI; document dependency reasons. Background research, desktop
control, all-day sensing, avatars, durable raw-media recording, multi-provider
support, and public APIs are outside this first proof. Cross-session continuity
(S33) and optional background coordination (S34) belong to M3.

The existing terminal/source code is prior work, not the presence demo. Retain
applicable S15/S20-S25 constraints from the [earlier scenarios](../history/M1-2026-09-17.md),
but full legacy A coverage is not a prerequisite. Record which branches apply.

## Delivery checkpoints

| Checkpoint | Observable result | Evidence |
|---|---|---|
| M2-P1 — Session and baseline | Fresh input after a reply ends; working sensor/session stop. | Configuration and limits; actual model/input smoke check for S26/S31. |
| M2-P2 — Participation | Grounded initiative, interruption, stale-output cancellation, receptive silence, and correction. | Early live owner inspection for S26-S30/S35; targeted control replays. |
| M2-P3 — Failures | Disconnect, exhaustion, late output, and restart cannot fake presence or revive stopped activity. | S28-S32/S35 replays and live input/output checks. |
| M2-P4 — Acceptance | Bounded shared activity compared with a thin direct-model baseline. | All exit criteria, including live and owner evidence. |

Controls and limits exist from P1. Early live inspection informs development;
M3 still waits for M2 acceptance.

## Record before the first live run

- Activity, selected inputs, host/UI, model/provider/version and capabilities,
  prompts, input/output formats, and dependency reasons.
- Numeric session duration, observation-age/buffer limits, output queue size,
  media/context bounds, timeouts, stop/interruption targets, and enforceable
  spending limits. Label targets, measured values, and estimates separately.
- Input grants, visible capture state, distinct stop controls, retained data,
  and reconnect policy. Restart or memory restoration must not activate capture.
- How interruption stops playback and cancels or invalidates generation;
  provider-native behavior versus Enthus additions. A bare `mute` label is
  insufficient for voice controls.

## Implementation and verification

Follow Roadmap's architecture invariants. Keep reception/stop controls responsive
while generation or tools run. Track session/output IDs and relevant observation
versions; bound queues and invalidate stale output. Distinguish generated, queued,
played, cancelled, and uncertain content. Do not remember a draft as fully heard
or replay interrupted speech. Precise usage may be estimated, but a conservative
host-enforced limit must exist. Expose disconnect/exhaustion; no compulsory farewell.

Maintain a scenario coverage map with positive/negative cases and remaining gaps.
Replays use timestamped inputs, controlled clocks/playback, and definite state
assertions. Live evidence uses actual changing inputs/model/output; label injected
or replayed material. Review withheld opportunities as well as interventions.

The thin baseline uses the same model, sensory access, activity, basic context,
and limits where possible. Record unavoidable differences and cases where Enthus
adds no value. Measure grounding, participation, interruption/staleness latency,
unwanted or missed contributions, and cost. Targets precede trial results.

## Exit criteria

- [ ] **M2-E7** (document) Session configuration, dependencies, CP/scenario coverage,
      numeric limits, and baseline/timing protocol are recorded before the corresponding
      live runs.
- [ ] **M2-E8** (live, owner) S26-S32/S35 are demonstrated through the actual input/output
      path, including stop and representative failure cases; the owner reviews grounded
      participation, receptive silence, correction, and interruption with limitations
      recorded.
- [ ] **M2-E9** (replay) S28-S32/S35 control and failure branches pass, with an explicit
      applicability map for retained S15/S20-S25 behavior; no stopped activity or stale
      output revives.
- [ ] **M2-E10** (live, document) The baseline and Enthus variant are compared on the
      bounded shared activity, including observed latency, missed/unwanted participation,
      and cost; native capabilities and Enthus contributions are separated.
- [ ] **M2-E11** (document) Session traces distinguish observation, proposal,
      dispatch/playback, cancellation, uncertainty, grants, and usage sufficiently to
      diagnose the recorded failures.
- [ ] **M2-E12** (owner, document) The owner accepts this bounded experience for sustained
      M3 evaluation; unresolved weaknesses, architecture strain, and the M2 handoff are
      recorded without claiming cross-session or background value.
