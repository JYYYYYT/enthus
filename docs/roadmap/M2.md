# M2 — Proactive Conversation MVP

> Status: pending
> Prerequisite reading: [Roadmap.md](../../Roadmap.md), [M1.md](M1.md)

## Goal

Let the owner experience an AI that can initiate grounded, worthwhile
conversation without an assigned work task, then continue naturally when the
user replies. Demonstrate the complete loop before extracting reusable APIs.

Primary scenarios: **S11–S25**. M2 establishes feasibility and basic quality;
M3 establishes whether the experience remains welcome over repeated use.

## What to build

1. **One bidirectional chat surface.** It must support unsolicited output and
   user replies in the same context; a print-only notifier is insufficient.
   A simple interactive terminal is acceptable if asynchronous output remains
   usable. Choose one surface, not a multi-channel platform.
2. **One queryable information source.** Support actual on-demand retrieval
   within configured scope and preserve provenance. Record source responses
   for replay and include empty/irrelevant/error outcomes in fixtures.
3. **Minimal memory.** Bounded core background, recent original messages and
   observations, and small topic notes with source references. Store current
   corrections separately from historical claims. Keep exact execution state
   out of semantic retrieval. Notes may initially be extracted during normal
   context processing; no lifetime summarization pipeline is required.
4. **One decider.** Given context, choose a concrete query, conversational
   message, wait, or end. Rules handle obvious gates; at most one structured
   model call per evaluation, with bounded steps for a multi-step exploration.
5. **A single-process run shell.** Accept user/source events and due wake-ups;
   coalesce events, build context, persist decisions, execute allowed actions,
   and return outcomes to the originating follow-up by explicit ID.
6. **Small persona and preference configuration.** Tone, message length,
   initiative limits, quiet hours, and enabled interests. Persona cannot
   override scope or resource/delivery constraints.
7. **SQLite persistence and recovery.** Store pending actions and events,
   waits, budgets, conversation context, mute state, and delivery records.
   Reliability belongs in this prototype, not only in a later extraction.

Before live use, record the chosen channel, source, model, dependencies and
reasons, context limits, global/per-exploration budgets, active-exploration cap,
expiry, initiation ceiling, cooldown, quiet hours, and mute defaults in this
file. These are tunable prototype settings, not universal policy defaults.

## Internal delivery checkpoints

Build incrementally in the order below. These checkpoints organize M2's work;
they do not replace its exit criteria or permit an early start on M3.

| Checkpoint | Smallest deliverable | Evidence before expanding |
|---|---|---|
| **M2a — Persistent conversation loop** | One chat surface, recent context, SQLite state, due wake-ups, one decider, and basic budget/mute/cancel gates. | User messages and replies share context; a wake can choose silence; a persisted wait survives restart. |
| **M2b — Bounded initiative** | One queryable source, topic notes, outcome feedback, and the three initiative behaviors. | Query → linked result → share or silence works; the user can continue the initiated topic; corrections affect queued output. |
| **M2c — Recovery and failure coverage** | Complete replay coverage for duplicates, late results, exhaustion, cooldowns, and unknown external outcomes. | S11–S25 have recorded checks; crashes do not cause blind resend or reactivate cancelled work. |
| **M2d — Live acceptance** | The actual model and source running through the chat surface under recorded limits. | Owner-reviewed examples include useful initiative and justified silence, with grounding and costs visible. |

Persistence and hard gates start in M2a; M2c exercises and completes their
failure handling rather than adding reliability as a retrofit. Keep the first
chat surface simple and reuse the same records throughout. An internal demo
does not establish that M2 is complete or that sustained use will be welcome.

## Execution contract

- Code handles dedupe, cancellation, grant checks, and resource accounting.
  Check before model calls and again before tool dispatch. Bound model output
  and tool time/cost according to the host's available controls.
- Keep decision generation separate from effect execution even in one module.
  State updates are validated and committed by the shell.
- Persist an action before dispatch. On completion, commit its outcome and
  pending follow-up event in one SQLite transaction. Recover unprocessed events
  after restart; closed or cancelled work cannot be reopened by late results.
- Distinguish failed from unknown outcomes. Use idempotency support where
  available; otherwise verify or require host resolution before retry.
- Observe quiet hours, initiation caps, mute, and active-conversation state
  before unsolicited delivery. A user reply does not clear the mute.
- Research results can be held, discarded, or shared. A query does not create
  an obligation to send a message. An exhausted exploration stops without a
  model-generated farewell or an exception to notification rules.
- Do not infer user interest from the AI's own messages or equate nonresponse
  with dislike. Explicit corrections take precedence over inferred notes.

## Scope boundaries

- One user, one channel, one source, one model; no distributed execution.
- No generic Attention/Policy/Arbiter plugin system or required Task/Interest
  class hierarchy. Plain functions and small internal records are sufficient.
- No vector database or recursive whole-history memory synthesis in this phase.
- Deployment watch remains an M4 validation scenario.
- Do not promise stable public interfaces or implement two independent runtimes.

## Verification

Maintain a scenario coverage map for S11–S25. Use a controllable clock,
scripted inputs, recorded tool/model responses, and asserted state/output
behavior for repeatable gate and recovery checks. Replays validate shell
behavior, not the model's ability to make good choices on unseen input.

Also run the actual model and source through the chat surface. Demonstrate
continuation of a shared topic, a grounded discovery, and an appropriate
reconnection, with a case where silence is the better choice. Each live example
must expose its relevant context, decision, source references, and actual cost
for owner inspection. Evaluate content as well as timing; trivial, repetitive,
or fabricated openings fail the example even if all gates passed.

## Exit criteria

- [ ] **M2-E1** (document) Host configuration and dependency choices recorded before live use.
- [ ] **M2-E2** (replay) S11–S25 covered by replayable scenarios, including mute, duplicate events,
      cancellation, resource exhaustion, and restart with an unknown send outcome.
- [ ] **M2-E3** (live) Three initiative behaviors demonstrated in the live bidirectional surface;
      the user can continue an AI-initiated topic with its original evidence.
- [ ] **M2-E4** (owner) Owner reviewed live examples for substance, continuity, grounding, timing,
      and burden; shortcomings recorded rather than hidden by scripted replays.
- [ ] **M2-E5** (document) Decision/outcome records include enough provenance, state, and usage data
      to diagnose failures and support M3's trial.
- [ ] **M2-E6** (document) Architectural strain recorded in M1 and a short `M2-NOTES.md` written for M3.
