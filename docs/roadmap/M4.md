## Goal

Use deployment watch as a genuinely different second scenario, then extract
the shared decision and runtime mechanisms. The validated conversation
experience is the starting point and must keep working throughout extraction.
Architectural changes prompted by the second scenario are findings, not failures
that must be concealed behind adapters.

## Second scenario: deployment watch

Implement S1–S10 with scripted deployment events, an inspect/query tool, a
notification sink, and an explicitly authorized task lifecycle. Reuse the
existing persistence and execution mechanisms where their contracts fit.

The work scenario must demonstrate continued checking without new instructions,
active investigation, waiting on ambiguous evidence, notification with evidence,
and clean stopping. Apply the shared mute rules and unknown-outcome recovery.
S8 additionally needs honest commitment status under exhaustion: reserved
reporting resources or host status, never a blanket disturbance-limit bypass.

Compare deployment decisions against fixed-interval checks plus simple threshold
rules on the same replayed incidents. Report useful interventions, misses,
noise, latency, and investigation cost. Preserve cases where rules are sufficient.

## Extraction process

1. Map conversation and work scenarios to the concrete code they use.
2. Separate reusable decision contracts from application context construction,
   memory selection, persona content, incident logic, and tool adapters.
3. Keep a decision core callable with one context snapshot. Let a reference
   shell own persistence, scheduling, grants, and execution.
4. Exercise the extracted core both from the reference runtime and a small host
   script that manages its own state/lifecycle. Each follow-up has one owner
   for scheduling and retries; avoid competing host and library runtimes.
5. Re-run both scenario families and inspect live conversation regressions.

A provisional target, to revise based on these findings:

```python
class DecisionEngine(Protocol):
    async def evaluate(self, context: ContextSnapshot) -> Decision: ...

class Executor(Protocol):
    async def execute(self, action: Action, *,
                      idempotency_key: str) -> Outcome: ...
```

Evaluation may call a model but does not send messages, mutate external
systems, or schedule timers. Decisions carry concise rationale, evidence
references, applicable state version, and usage metadata. A separate policy
or arbitration layer is justified only if the scenarios need it.

## Contract and integration requirements

- Exact execution and budget state stays separate from semantic memory.
  Topics and active follow-ups may be linked without forcing a one-to-one model.
- Generic routing uses stable identity, not payload interpretation.
- Public event/action payloads have a defined serialization contract.
- Established extension surfaces use `typing.Protocol` and complete types.
- Provide small convenience adapters where exercised, rather than a broad
  plugin registry. Memory and persona may remain host-owned.
- Record limitations of external effects, recovery, and model nondeterminism.
  A stored decision rationale is not a complete internal reasoning trace.
