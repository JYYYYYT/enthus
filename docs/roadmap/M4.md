# M4 — Aliveness Family: Interest Concerns and Persona

> Status: pending
> Prerequisite reading: [Roadmap.md](../../Roadmap.md), [M1.md](M1.md), [M3.md](M3.md)

## Goal

Prove the architecture is **general**, not a deployment-monitor script in
disguise, by running the aliveness family (scenarios S11–S15) on the same
decision core. No new core machinery should be needed — only new policies,
a second concern class, and configuration. If the core must change, that
change is the real deliverable of this milestone; record it.

## What to build

1. **Interest concerns**: no success condition; lifecycle is refresh and
   decay; separate "wandering" budget isolated from task budgets.
2. **Persona config**: tone, per-policy weights and thresholds, interest
   lists — pure data, loaded by the host. The framework stays
   persona-neutral.
3. **A social policy**: proposes greetings and shares (S11), informed by
   memory of recent interaction.
4. **Disturbance budget as a hard gate**: quiet hours, daily initiation
   caps, per-channel throttles (S12, S14) — constraint layer, never a
   policy score.
5. **Observation actions within granted scope**: active perception for
   interest concerns, bounded by `action_scope` (S13).
6. **User-level muting**: interest concerns silenced while task concerns
   continue (S15).

## Explicit non-goals

- No humor engine, no roleplay framework. Persona configs are data; content
  quality of drafts is the host model's problem.
- No open-ended multi-agent social simulation.

## Verification approach

S11–S15 are harder to score objectively than the work family. Use:

- Scripted interaction timelines (absence, late-night finding, topic
  drift, over-talkative day, muting) replayed deterministically.
- Owner review of each intervention: was it welcome, timely, and
  well-judged? A small rubric (would this annoy me if it happened daily?)
  beats a numeric score here.
- The disturbance gates must be exercised to failure at least once: prove
  a high-scoring action gets vetoed and held (S12) and that restraint
  happens with a visible record (S14).

## Exit criteria

- [ ] S11–S15 demonstrated on the M3 core without core changes, or every
      required core change documented and justified.
- [ ] Persona swap demonstrated: same scenario, two configs, visibly
      different initiative levels.
- [ ] Written comparison: which abstractions held across both families —
      those become M5 stabilization candidates.
